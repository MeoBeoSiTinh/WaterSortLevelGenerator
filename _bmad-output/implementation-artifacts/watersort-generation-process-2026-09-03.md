# Water Sort Generation Process Record — 2026-09-03

This document records the Water Sort level-generation and solution-solver decisions made on 2026-09-03.

## Objective

Build a repeatable process for generating 100 Water Sort levels with matching solution JSON, including larger boards and longer solution paths, while preserving runtime hidden-stack rules.

## Reference Findings

The folder `Assets/Project/Data/WaterSort/Resources/Ref` was analyzed as design reference only.

Findings kept in the rules:

- Ref data stores layouts, not explicit solution paths.
- Current-compatible behavior is classic Water Sort:
  - move: pour matching top color group;
  - win: every non-empty bottle is mono-complete.
- Capacity 4 is the safest default.
- Compact reference layouts usually use 2-3 helper bottles.
- Wide layouts can use 16-30 containers while keeping distinct color count stable.
- Runtime JSON should not copy reference-only metadata such as source IDs, original mode names, positions, `gid`, palette names, or source-game flags.

## Runtime Rule Alignment

Gameplay was updated around hidden-stack behavior:

- only the top layer is visible/unlocked initially;
- hidden layers render black with `?`;
- locked hidden layers cannot move;
- moving/removing visible top layers reveals the next layer below;
- solver validation must obey the same rule.

## Layout Quality Decisions

The generated layout rules were tightened:

- reject full mono starting bottles;
- reject any bottle where a color appears `capacity` times;
- prefer no repeated color inside a bottle;
- prefer non-adjacent repeated pairs over adjacent repeated pairs;
- allow triples only rarely and with maximum separation.

This prevents generated starts such as `[c, c, c, c]`.

## Solver Work

Added:

- `_bmad-output/implementation-artifacts/watersort-exhaustive-solver.js`
- `_bmad-output/implementation-artifacts/solve-watersort-solutions.js`

Solver capabilities:

- hidden-stack state;
- legal hidden-stack pour;
- BFS shortest search for small boards;
- first-winning-depth solution counting;
- representative stored paths;
- replay-compatible 1-based move output;
- optional pruning/canonicalization:
  - skip completed full mono source;
  - skip symmetric whole-mono-stack moves into empty bottle;
  - canonicalize bottle-order states;
  - canonicalize color-label states;
  - lower-bound max-depth pruning.

Important limitation:

- Whole-board BFS is still too expensive for many 16-30 bottle boards.
- A full 30-bottle board cannot currently be guaranteed global-shortest in practical generation time.

## Generator Work

Two generator paths now exist.

### Scramble-Based Generator

File:

- `_bmad-output/implementation-artifacts/generate-watersort-100.js`

Purpose:

- historical/experimental generator;
- generated by inverse scramble from solved state;
- useful for testing layout scoring;
- not the preferred path for current wide modular packs.

Limitation:

- produced boards that often exceeded BFS limits.

### Config-Driven Modular Generator

File:

- `_bmad-output/implementation-artifacts/generate-watersort-exhaustive-100.js`

Current intended generator.

Behavior:

- reads `WaterSortGenerationConfig.asset`;
- uses config bands for level ranges, bottle limits, step limits, color weights, capacity chance, pack size, and solution policy;
- solves small modules with hidden-stack BFS using concrete paths;
- composes modules into larger boards;
- remaps colors and bottle positions;
- replay-validates stored paths on the final concrete board;
- supports dry-run via `WATERSORT_GENERATOR_DRY_RUN=1`.

Policy:

- modular solutions are valid constructed paths;
- they are not automatically global shortest;
- `selectionPolicy` must state this clearly.

## Empty Bottle Issue and Fix

Problem found:

- Early modular generation added 2 empty bottles per module.
- Large levels ended up with too many empty bottles, making them easier than config intended.

Fix direction:

- read `preferredMinEmptyBottleCount` and `preferredMaxEmptyBottleCount`;
- avoid uncontrolled empty bottles per module;
- limit module count/helper count within config;
- validate empty count in dry-run.

Latest dry-run after the fix:

```json
{
  "minEmpty": 1,
  "maxEmpty": 3
}
```

## Main/Late Pacing Issue and Fix

Problem:

- Long hard levels could appear consecutively for too long.
- Bottle count behaved too much like a one-way ramp.

Fix direction:

- Main and Late use pacing profiles:
  - hard;
  - hard;
  - medium;
  - hard;
  - relief.
- Relief levels target shorter paths.
- Relief levels do not drop bottle count too far below their band.
- Bottle count is sampled from the config-derived range rather than monotonically increasing.
- Relief/medium levels can store more representative constructed routes.

## Commands

Dry-run:

```powershell
$env:WATERSORT_GENERATOR_DRY_RUN="1"
node "_bmad-output/implementation-artifacts/generate-watersort-exhaustive-100.js"
```

Generate data:

```powershell
Remove-Item Env:WATERSORT_GENERATOR_DRY_RUN -ErrorAction SilentlyContinue
node "_bmad-output/implementation-artifacts/generate-watersort-exhaustive-100.js"
```

Solve a range:

```powershell
node "_bmad-output/implementation-artifacts/solve-watersort-solutions.js" --levelFrom=1 --levelTo=10 --maxDepth=120 --maxStates=300000 --write=false
```

## Current Recommendation

For the next real generation:

1. Edit `WaterSortGenerationConfig.asset` first if band ranges should change.
2. Run modular generator in dry-run.
3. Inspect by-band step, bottle, empty, relief/medium/hard counts.
4. Generate real JSON only after dry-run stats are acceptable.
5. Replay-validate all stored solutions.

Do not claim modular composed levels are globally shortest unless whole-board solver proves it.
