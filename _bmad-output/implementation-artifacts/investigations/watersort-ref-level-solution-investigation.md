# Investigation: Water Sort Ref Level Design And Implied Solution Logic

## Hand-off Brief

1. Confirmed: `Resources/Ref` is a normalized reference corpus of level layouts and mode metadata from LogicColor, GetColor, ASMRWaterSort, and NutSort.
2. Confirmed: no explicit solution-path schema such as `solutions`, `solutionData`, `stepCount`, `fromBottle`, or `toBottle` exists in Ref JSON.
3. Deduced: solution information for Ref levels must be generated by applying the canonical move rule and a solver to each layout, not read directly from Ref.

## Confirmed Findings

### Ref Shape

Ref level files use `watersort-level/v2`. Top-level files group levels by canonical mode and source game. Each level has `uid`, `game`, `orig_id`, `source_mode`, `capacity`, `containers`, `num_containers`, `num_colors`, `invariant_ok`, and `canonical`.

### Ref Solution Availability

Exact searches found no `solutions`, `solutionData`, `stepCount`, `fromBottle`, `toBottle`, `answer`, or `hint` keys in Ref JSON. Ref stores layout state and canonical rule metadata, not explicit shortest-solution paths.

### Implied Solution Logic

The relevant Ref fields are `canonical.move = pour_top_match` and `canonical.win = mono_all`. A solution is therefore derived by solving the layout under that rule: pour the contiguous top color group from a source into an empty target or a target with the same top color, until all bottles are empty or mono-complete.

## Deduced Generation Logic

- Build a solved target distribution first: each target bottle is mono-color and full.
- For compact classic levels, use one target bottle per color.
- For wide 16-30 bottle levels, keep distinct colors stable and create duplicate target bottles for existing colors.
- Scramble from the solved state through legal reverse pours or construct a mixed layout that preserves exact color totals.
- Validate with a forward solver using top-match pour rules.
- Accept only layouts whose shortest solution count and shortest step count match the intended band.
- Store only layout in Ref-style data; store generated solution metadata separately if converting into runtime JSON.

## Deduced Difficulty Logic

- Early levels ramp color/container count quickly.
- Main progression plateaus instead of increasing forever.
- Difficulty changes through a mix of color count, helper/free slots, empty bottle count, top-run fragmentation, partial bottles, no-empty starts, and special mechanics.
- LogicColor/GetColor are best references for compact classic generation.
- NutSort is best reference for classic `colors + 3` helper layouts.
- ASMRWaterSort is best reference for 16-30 visible bottle layouts with fewer distinct colors and duplicate/repeated color targets.

## Conclusion

Confidence: High for Ref structure and absence of explicit solution paths; Medium for inferred generation process because Ref does not include source generator code.

Ref should be treated as design/statistical input. It gives canonical mode, move rule, win rule, layouts, native ordering, and progression shape. It does not give explicit solution paths, so any "solution of Ref levels" must be produced by a solver and then stored separately in runtime solution JSON.
